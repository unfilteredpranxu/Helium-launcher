# G02-A: expanded terrain and a scalable Metal baseline

Source baseline: `6dad41aca3a52eb5dae2375c33195e02e8f04479`, branch
`feature/helium-g01-metal-prototype`. MIT; Copyright (c) 2026 Ludovic Marie and
the Horizon contributors. Existing licenses and attribution are retained.

This is an independent experiment, not a production backend selection. Production
wgpu rendering, launcher, game logic, world generation/storage and dependencies are
untouched. No CI or Apple build is authorized by G02-A. The owner has established
that G01 runs on iPad A16/iPadOS 27.3, with one 0.000252 s offscreen render/blit
measurement. That is not gameplay FPS and does not validate G02 or A11 performance.

## Verified production contract

The source, rather than a new mesher or simulation, defines this interface:

| Field | Byte offset | Encoding |
|---|---:|---|
| pos | 0 | Three f32, section-relative, including fractional model offsets |
| uv | 12 | Two u16, 32768 steps/unit for sections, range [0,2) |
| layer | 16 | u16; bit 15 OPAQUE_LAYER, lower 15 bits sprite identity |
| light | 18 | u16; low byte sky, high byte block, each 16 steps/level |
| color | 20 | u32; low byte R, then G/B, high byte metadata; RGB contains tint, face shade and AO |

Stride **24**, alignment **4**, no padding. Sources: production
`crates/horizon-client-render/src/mesher.rs:60-143`, `:1257-1300`, and
`gfx.rs:29-31`. Important: color's high byte is emission/fluid metadata, not
ordinary opacity. It is preserved byte-for-byte; SDR solid shading uses RGB and
sprite alpha. The opaque layer flag suppresses cutout. `terrain.wgsl:642-655`
uses a **0.5** cutout threshold, not 0.1.

`gfx.rs:5106-5115` uses `[0,1,2,0,2,3]` per quad. The adapter does not change
indices, corner order, diagonal or winding. `gfx/view.rs:14-40` supplies column-major
camera-relative matrices with reversed Z (near=1, far=0); production terrain uses
GreaterEqual. New default depth is GreaterEqual/clear 0, with an explicit
LessEqual/clear 1 forward-depth option for validation. G01's Less/clear 1 is unchanged.

`terrain.wgsl:300-336,581-610` decodes section UVs and samples a 16x16 lightmap
at `(block,sky)/16 + 0.5/16`, clamped to texel centers. The new vertex shader
preserves fractional light, samples an uploaded linear RGBA8 lightmap, and multiplies
already-baked RGB. The test lightmap is synthetic; it does not recreate the game's
time/weather/gamma-dependent lightmap generator. Production sprite sampling uses
clamped linear sampling plus sampleNearest/RGSS and mip logic (`terrain.wgsl:105-207`,
`gfx.rs:1661-1676`). G02 deliberately uses clamped point sampling, one mip, and the
same UV wrap convention. Filtering parity is not claimed. Production instance
`origin.w` also encodes UV step and fade; it must not be copied blindly into the
new View. G02 separates xyz origin from the fixed section UV step. Chunk fading
and tiled LOD UVs are not implemented. Backface culling remains disabled; the
input winding is preserved, but culling parity is not established.

`mesher/packed.rs:1-32,51-122,204-240` additionally stores eligible integer-grid
quads as one **24-byte quad record**, with FULL records for unrepresentable geometry.
Those are NOT 24-byte vertices. G02 consumes expanded TerrainVertex streams, not
packed records. Full sprite-bank splitting, packed-quad decoding, translucent
sorting/blending, HDR emission, dynamic light/fog and shader packs remain unsupported.

## Implementation and ownership

`src/terrain.rs` defines the contract, platform-independent preflight and budgets.
`Mesh::from_vertices` borrows the local padding-free type without allocating.
A future production adapter can pass `bytemuck::cast_slice(section.solid)` and its
indices into `Mesh`; this experiment need not depend on the production crate or wgpu.
Arbitrary byte alignment is accepted; validation reads little-endian scalars rather
than forming aligned Rust references. Raw input must be expanded vertices, not records.
The 16-byte G01 type is never reinterpreted; its fixture conversion is CPU-test-only.

`src/terrain/metal.rs` owns a persistent MTLDevice, command queue, compiled pipeline
and two depth states. The actual device capability record is exposed read-only;
caller-created CPU capability records cannot replace the renderer's queried limits.
Per-request code validates sizes/budgets before scanning geometry or allocating GPU
buffers. It checks finite positions/matrices/origins, every index, flat triangle layers,
texture lengths, and checked arithmetic. Each Metal buffer is checked against actual
maxBufferLength and Rust allocation bounds. The uploaded lightmap must be opaque 16x16 RGBA.

`src/terrain/terrain24.metal` uses **packed_float3**, ushort2, ushort, ushort, uint,
with stride/alignment/offset static assertions. A regular MSL float3 would break
the ABI. Vertices go directly into copied Metal buffers without repacking positions,
UVs or flags. Uniforms carry a column-major matrix and camera-relative section origin.

Atlas/lightmap texels use initialized, 256-byte-row-aligned shared staging and
blits into private textures; the same allocation path accommodates discrete Macs.
One normal retaining command buffer orders upload blits, render and readback.
Color is cleared/stored; depth is cleared/discarded. Only initialized pixel prefixes
are copied from padded readback rows, after Completed status. Retained owners and
the autorelease pool live through completion. No borrowed image memory escapes.
Nil allocations, pipeline/compiler errors and command errors return diagnostics.
Objective-C exceptions/driver hangs are still not recoverable; the blocking probe
belongs on a worker, with no timeout, never a gameplay rendering loop.

## Device scalability and limits

Minimum deployment target remains **iOS 15**, so iPhone X/iOS 16 is not excluded.
The same baseline is intended for A11, A12, A13, A14, A15, A16 and later compatible
devices. Physical validation of G02 on every such family is **NOT RUN**.

Initialization queries `supportsFamily` for OS-available Apple/Common/Mac families,
`maxBufferLength`, and `supportsTextureSampleCount`. Optional selectors for unified
memory, recommendedMaxWorkingSetSize, currentAllocatedSize and argumentBuffersSupport
are checked with respondsToSelector. Missing values remain None, never guessed from
device names or RAM tables. Newer family enums have OS guards. A recognized Apple4+
or Common1+ baseline is required; unknown hardware gets an error rather than inferred
features. Single-sample support is required. No optional feature is enabled merely
because a newer family exists. Argument buffers, ICBs, memoryless attachments, MetalFX,
tile shaders and counters are not required or enabled.

Metal has no general scalar maxTextureDimension2D query. **4096 pixels and 256 array
layers are conservative experiment policy ceilings, not reported hardware maxima**.
They keep requests inside the selected core baseline; allocation can still fail.
They also mean that a full production sprite atlas may require a future bank adapter
and explicit family-table validation before lifting these ceilings. Runtime device
limits remain authoritative for buffers. Consult Apple's Metal feature tables when
adding optional formats/features: https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf

Options supports variable target width/height, explicit depth convention and workload
budgets; format remains RGBA8Unorm/Depth32Float, single sample. The default 32 MiB
tracked payload and 1M target pixels are **probe policy**, not an A11/A16 memory limit
or automatic quality tier. Payload accounting includes known GPU resources and CPU
staging/output copies, but excludes driver texture padding, pipeline memory, caller
inputs and retained earlier results. Recommended working set is advisory, not free
RAM or a jetsam guarantee. There is no automatic resolution/thermal/profile controller.

## Deterministic evidence and remaining Apple tests

CPU tests cover exact little-endian vertex bytes/offsets/alignment, unaligned byte
inputs, fractional geometry and UVs, flags, multiple layers, lighting channels,
quad topology, invalid indices/streams, finite values, memory/pixel limits, overflow,
staging/readback padding and compatibility with G01's 184-vertex/276-index fixture.
The readback regression leaves row padding uninitialized and copies only pixel bytes.

The new material chart is 16 vertices/24 indices, three original 2x2 texture layers
and an analytic 16x16 lightmap. Nonzero section origin and a nonidentity clip matrix
exercise camera conventions. UVs above one exercise wrapping. Overlapping faces,
opaque override, alpha values 0/127/128/255, baked tint, and fractional sky/block
lighting have independent expected results. Four complete material regions and the
background are checked across **all 65536 pixels**, with RGB tolerance 2 UNorm codes
and exact alpha. A blank image, 101 colored pixels, a wrong visible material,
missing foreground depth, or invalid alpha fails. The oracle's synthetic reference
is used only in CPU tests, never as a GPU result.

On Apple, `terrain::smoke_test` renders normal order, reversed triangle order and
equivalent forward depth; all must pass the full oracle. The first two images must
also match exactly. Timing covers the first command's **uploads + render + readback**,
excluding pipeline creation; it is neither gameplay FPS nor comparable to G01's
different workload. These G02 GPU tests and MSL compilation are **NOT RUN** here.

After owner review, exact Apple commands from the repository root (NOT RUN):


The additive `helium_metal_terrain_test_rgba` C entry has the original caller-buffer
contract and returns real pixels only after every new oracle check passes. At the
G02-A baseline the SwiftUI app still called only G01 and CI compiled only G01's shader;
no UI or production launcher was changed. G02-C adds selection and prepares separate
shader compilation in the [standalone iOS host](../ios/README.md). Previous G01 success
must not be reused as G02 shader or runtime evidence.

## Optimization research: ranked hypotheses, not measured improvements

Value below means investigation priority, not an established speedup. Production
`gfx/upload.rs` already reuses a staging belt; `gfx/timing.rs` uses delayed queries,
and `spans.rs`/horizon-bench provide CPU/reporting infrastructure. Reuse their data
contracts and workload definitions; wgpu resource handles cannot cross into Metal.

| Rank / candidate | Compatibility and cost | Correctness risk | Practical comparison |
|---|---|---|---|
| 1. Reuse buffers/targets and batch streaming uploads | All baseline devices; medium; bounded ring/arenas, completion-based reuse | High if overwritten while in flight; memory budget must include every slot | Fixed mesh update trace; CPU allocations/time, upload bytes, Metal allocated bytes, GPU command time |
| 2. Packed quad vertex pulling | Baseline vertex_id; medium; reuse production packing eligibility and explicit full-vertex fallback | High: exact positions, UVs, light and flags must round-trip; no quantization of plants | Packed record is 24B versus four 24B vertices (structural fact); measure bandwidth, decoder ALU and GPU time on A11/A16 |
| 3. CPU frustum/section visibility plus opaque-first draws | Baseline; medium; no ICB dependency | High for false culls or stale bounds; opaque/cutout separation must respect flags | Identical camera traces, oracle/reference images, visible counts and frame-time tails |
| 4. Tile-friendly pass merging/store policy | Core load/store baseline; medium; optional memoryless/tile features need family/format checks | Medium/high: merging must preserve dependencies/order; attachments cannot be discarded before consumers | Capture passes and external-memory counters where available; compare GPU time/energy. G02 already discards unused depth |
| 5. Resolution/workload budgets | All baseline; medium; existing Options varies target size, controller absent | Medium: HUD separation, aliasing, oscillation and image stability | Fixed thermal-state scenes, image quality, p95/p99 frame times; compare simple scaling first |
| 6. Hierarchical/temporal occlusion | Baseline compute if verified; high; conservative CPU visibility fallback | High: camera cuts, edits, disocclusion and latency can hide real terrain | Dense/open scene traces with deliberately invalidated history; false-negative count must be zero |
| 7. GPU-driven/ICB submission | Optional; high; verify specific family/API/ICB limits, not argument tier alone | High: indirect ranges, barriers, residency and resource lifetimes | Same draw lists via CPU and GPU; CPU encode time, GPU time, visible-set identity |
| 8. Distant meshes / silhouette impostors | Baseline reduced geometry; high; reuse existing LOD state later | High: seams, saves/cache separation, lighting and temporal transitions | Controlled terrain flythroughs; memory, triangles, transitions and sustained frame pacing |
| 9. MetalFX or temporal reuse/upscaling | Optional OS/device support via runtime supportsDevice checks; high; ordinary spatial scaling fallback | High: motion vectors, history, ghosting, sample jitter | Matched output resolution/quality, disocclusion scenes, GPU cost and peak memory; never assume A11 support |
| 10. Thermal-aware scaling | iOS thermal notifications available to baseline; medium; gradual, reversible workload policies | Medium: oscillation and excessive quality loss | Long physical-device runs with warm-up, thermal states, energy and p50/p95/p99 pacing |

An additional experiment worth considering is a hybrid packed/unpacked arena with
small material/exposure palettes: share repeated face data, keep exact floating-point
fallbacks. It may trade bandwidth for dependent loads/ALU, especially on older GPUs.
Cost medium/high; risk high for ordering and palette lifetime. Compare cache misses,
uploaded bytes and sustained GPU time against the existing expanded and packed formats.

CPU/GPU overlap needs a bounded in-flight queue with completion-protected resource
slots; CPU submission must not wait for every frame as this diagnostic probe does.
Validate immutable mesh revisions once when uploaded, rather than rescanning every
frame. These scheduling/caching changes are candidates, not implemented optimizations.

All comparisons need equivalent meshes, camera, lighting, targets and quality;
include readback equally or exclude it equally, and separate compile/upload/render
costs. Use deterministic fresh synthetic data, not real player worlds. Measure A11
and newer physical devices over sustained runs before selecting any optimization.
30/60 FPS goals remain targets, with no comparative performance claim from G02-A.
