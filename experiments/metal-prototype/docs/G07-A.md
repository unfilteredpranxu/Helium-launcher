## Epoch audit — confirmed missing render-client propagation

At baseline `Game::new` constructs Controllers for both the render client and
integrated server (only split guest excluded). `game/integrated.rs` creates a
second Game with `ExecutionRole::IntegratedServer`; server world installation (`finish_open_world`, reached from `load_world` or integrated startup) calls
`world_changed` at game.rs:13453. Render client's `remote.rs::join_server` and
client-level replacement install new streamers/worlds without that notification.
`Controller::new` initializes epoch 0; `allocate(self.world_epoch)` records that
value. Thus server epoch 1 does not prove the rendering Controller has epoch 1.
This is a source-confirmed route for the discrepancy, not private-log instance
tracing or proof that every owner event took this exact path.

Fix: only client execution roles construct a Controller. Render-client streamer
installation (join and actual new client level) calls `world_changed`; leave
revokes. Each change gets a process-unique monotonic epoch, not a save identifier.
Admission rejects no-world epoch 0. Tests verify different Controllers and new
worlds do not share epochs, and cancellation retains ownership. Old callbacks
remain keyed to exact attempt id and cannot publish a later Gate.

### Lifecycle state diagram — current versus required

```text
Foreground dirty world
  → resign-active / background
      current: native cancellation + occlusion; no proven early durable-save lease
      missing: coordinated save request and applicable host-owned background time
  → [ordinary close] cooperative stop → snapshots → writes queued (NOT DURABLE)
      → component sync acknowledgement → all-world durable confirmation (NOT PROVEN)
      → world retired → worker joins → lock released → exit
  → [native process-exit callback] synchronous save/poll/join/drop on event thread
      → may exceed 5-second FRONTBOARD budget → SIGKILL
  → [unexpected kill] no callback or destructor guaranteed
      queued-only memory is lost; no durable replay journal exists for those writes
```

Disk/encoding/drain/join belong on owned workers, with UI polling a status that
cannot block or invent completion. A normal close and an abrupt host exit are
not interchangeable. beginBackgroundTask in Launcher/GameFiles.swift covers file
import, not world saves; it is not reused here. An API call in willTerminate does
not create an assured extra five seconds or override a host's process-exit policy.
The safe background-task/expiry ownership protocol remains unimplemented.

### Minimal safe implementation and source-proven fixes

- **Actual false-completion defect reproduced first:** a failed async player write
  is reported as error, then writes_finished consumes that error and the next poll
  returns complete without retrying it. New real filesystem test failed at that
  second poll. Errors now remain sticky; successes for unrelated players and a
  restarted transport do not acknowledge failed/lost work. Older tests which
  expected this false recovery now require the error to remain.
- Async player completion now uses the existing write_dat_durable helper: temporary
  file sync, replacement and parent-directory sync, before successful acknowledgement.
  save_after uses the durable result and records failure. Save_game/metadata's
  player barriers propagate errors rather than discarding them. This fixes these
  component acknowledgements, **not all-world durable shutdown**. Other metadata
  paths and recovery still require audit/coordinator work.
- SaveDir::try_write_status is a nonblocking observation of outstanding batches,
  pending records and sticky errors. flush_until is a bounded **worker-side** drain.
  False means still pending: it does not detach, drop storage, release a session
  lock, or claim data recoverable. Existing blocking Drop is intentionally retained.
- Numeric shutdown tracing records queue/start/synced/error, drain/deadline,
  actual region/player/server joins and streaming/LOD waits, event-thread identity,
  anonymous storage-instance IDs and elapsed monotonic time. Native cancellation
  precedes main exit saving. App now forwards the existing suspended handler,
  which was previously swallowed by its ApplicationHandler wrapper.
- Reporter has 128 timeline records, 16 protected first errors and 16 active
  waits/joins, totals/loss counters; no paths, player identities, seeds, NBT or raw
  error text. A report worker owns only numeric snapshots and the log destination.
  It never owns or joins a world/save worker. While a join is pending it refreshes
  elapsed evidence at most once a second; otherwise it writes only changed state.
- Current/previous numeric snapshots are normalized into the single existing
  Documents/logs/Helium-Metal-Report.txt. Same-boot correlation uses the recorder's
  boot ID; foreign current traces are refused. Storage IDs are **not** renderer
  world epochs. Unknown associations are explicit, not copied from the wrong Game.
  The five-second near-deadline indicator is relative to an observed wait, not a
  measured Frontboard deadline. Persistence is best effort and not an fsync promise.
- Lower renderer/thread cleanup hooks carry only enum values and a function pointer;
  no Game reference, UIKit pointer, unsafe Send/Sync or changed worker scheduling.
- Packaging contains an unconditional P0 hold before any owner IPA operation.
  No manual input bypass exists. Signed production workflows/entitlements and
  native capture shaders/textures are unchanged. No new owner artifact is emitted.

### Dirty-write timeout behavior and durability tests

Controlled temporary fixtures only; no owner world, stress or repeated device

### Unresolved P0 exposure — release blocker

Main/event-thread termination can still synchronously wait for server/player/
region/LOD cleanup. No complete owned nonblocking shutdown state machine spans
all dimensions, metadata, players, session lock and late worker errors. No durable
journal/replay covers queued-only data if the host kills the process. Source error
paths and guest-code/image lifetime under LiveContainer still require this
coordination. Simply detaching a thread or releasing the lock at timeout would
convert an observable watchdog into unacknowledged save loss and is rejected.
`Game::shut_down` still warns and continues teardown after `save_for_exit` fails.
The sticky player error is neither a retry nor a persisted copy of its failed
snapshot. Region failed snapshots remain readable only while their SaveDir is
owned. Neither component supplies a recovery transaction for a killed process;
those error and ownership paths must be covered by the missing coordinator.

The new component fixes/tracing are **PARTIAL**. They do not establish save loss
in the owner's crash, do not prove the main join's identity and do not establish
safe five-second all-world exit. No general guarantee is possible for a forced
kill while writes are still pending. A recoverable persisted handoff/journal or
another tested non-destructive isolation is required before owner distribution.
Shutdown trace storage IDs do not yet provide the requested end-to-end world-epoch
correlation across server/player/cleanup roles. Its first 16 failure records are
protected globally, not an unlimited or complete failure history. Those limits,
and best-effort trace persistence, also preclude treating this instrumentation as
the completed shutdown contract. The native capture's separate nonzero world-epoch
admission and cross-session tests are unchanged.
